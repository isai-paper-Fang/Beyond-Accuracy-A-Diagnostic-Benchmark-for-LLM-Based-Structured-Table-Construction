## 1. สัญญา output — ใช้เหมือนกันทั้ง 18 ชุด

ข้อความบล็อกนี้ต่อท้าย prompt ทุกชุด **ห้ามแก้แม้แต่คำเดียวระหว่างชุด** เพราะเป็นตัวแปรที่ต้องคุมให้คงที่

```
รูปแบบคำตอบ
1. อธิบายวิธีคิดของคุณเป็นข้อความอิสระก่อน ยาวเท่าที่ต้องการ
2. จากนั้นปิดท้ายคำตอบด้วยบล็อกโค้ด json เพียงบล็อกเดียว
3. ในแต่ละรายการของบล็อก json ให้เขียนฟิลด์ "เหตุผล" เป็นฟิลด์แรกเสมอ
   แล้วจึงตามด้วยฟิลด์อื่น
4. ถ้าข้อมูลใดไม่ปรากฏในเอกสาร ให้ระบุว่า "ไม่มีข้อมูล" ห้ามคาดเดา
5. ตอบเป็นภาษาไทย ตัวเลขให้เขียนเป็นเลขอารบิกโดยไม่ใส่เครื่องหมายคั่นหลักพัน
```

### 1.1 การตัดสินใจที่ฝังอยู่ในสัญญานี้

| ข้อ | ที่มา | ชั้น |
|---|---|---|
| ไม่ใช้ JSON-mode / constrained decoding | OF-01 · Tam et al. 2024 | L1 |
| **ไม่ใส่ JSON Schema เข้มงวด** ระบุชื่อฟิลด์เป็นภาษาธรรมชาติในเนื้องานแทน | OF-02 / R1 · Tam et al. ตารางที่ 1 | L1 |
| **ฟิลด์เหตุผลมาก่อนฟิลด์คำตอบ** (ข้อ 3) | OF-03 / R2 · 100% ของคำตอบ JSON-mode จาก GPT-3.5 วางคีย์ answer ก่อน reason | L1 |
| ข้อความอิสระก่อน แล้วปิดท้ายด้วยบล็อก json | OF-04 — **นี่คือ FRI ที่จัดลำดับคีย์ ไม่ใช่ NL-to-Format** | L3 |
| ข้อ 5 ห้ามใส่ลูกน้ำคั่นหลักพัน | ลด parsing error ที่ไม่เกี่ยวกับ construct | L3 |

### 1.2 ⚠️ ข้อ 4 — จุดที่ต้องประกาศตรง ๆ ในบทความ

ประโยค **"ถ้าข้อมูลใดไม่ปรากฏในเอกสาร ให้ระบุว่าไม่มีข้อมูล ห้ามคาดเดา"** ทำให้กับดักตระกูล B ง่ายลง เพราะเป็นการอนุญาตให้ปฏิเสธอย่างชัดแจ้ง

**เหตุผลที่ยังใส่:** ถ้าไม่ใส่ โมเดลที่ผลิตตัวเลขขึ้นมาจะเถียงได้ว่าทำตามคำสั่ง ("จงกรอกตารางให้ครบ") การวัดการปฏิเสธจึงต้องมีเงื่อนไขว่าการปฏิเสธเป็นทางเลือกที่ถูกต้อง — ตรงกับช่องว่าง "การวัดการปฏิเสธ" ที่ HalluLens ระบุเอง

**เขียนในบทความว่า:** เราให้สิทธิ์ปฏิเสธอย่างชัดแจ้งเท่ากันทุกเงื่อนไข ค่าที่วัดได้จึงเป็น *ขอบล่าง* ของอัตราการกุ ไม่ใช่อัตราที่จะเกิดในการใช้งานที่ไม่มีคำสั่งนี้ · **ชั้น L3**

## 3. ตารางตรวจ D4 — ห้าม prompt ใบ้ว่ามีกับดัก

| งาน | คำที่อาจถูกมองว่าใบ้ | ทำไมยังเก็บไว้ |
|---|---|---|
| T1 | "ความครบถ้วนของข้อมูล" | ชื่องานตาม HANDOFF §2.4 คือ **สรุปยอด + ตรวจค่าหาย** การถามความครบถ้วนจึงเป็นตัวงาน ไม่ใช่คำใบ้ · และไม่ได้บอกว่ามีค่าเฝ้าปลอมตัวอยู่ ซึ่งเป็นส่วนที่ยากจริง |
| T3 | "เป็นบาท" · "ใช้จ่ายจริง" | ระบุหน่วยที่ต้องการเป็นข้อกำหนดปกติของงานรายงาน ไม่ได้บอกว่าหน่วยในเอกสารปะปน |
| T5 | "หนึ่งรายการต่อหนึ่งกลุ่มเป้าหมาย" | เป็นการระบุรูปร่างผลลัพธ์ ไม่ได้บอกว่ามีเซลล์หลายค่า |
| T6 | "ควรตรวจสอบเพิ่มเติม" | บังคับตาม R3 · ถ้าไม่ถาม จะไม่มีอะไรให้วัด |
| T7 | "อ้างอิงได้จากเอกสาร" · "ความสอดคล้อง" | เป็นข้อกำหนดของงานสกัด claim ไม่ได้บอกว่ามีตัวเลขขัดกัน |
| ทุกงาน | "ห้ามคาดเดา" (สัญญา ข้อ 4) | ดู §1.2 — ทำให้ตระกูล B ง่ายลง ต้องประกาศในบทความว่าค่าที่วัดได้เป็นขอบล่าง |

**คำที่ไม่ปรากฏใน prompt ใดเลย:** ข้อผิดพลาด · ผิดพลาด · ตรวจจับ · ระวัง · กับดัก · ซ้ำ · หน่วยไม่ตรง · ค่าผิด · ผิดปกติ

## 4. รูปร่างผลลัพธ์ที่ `scorer.py` ต้องรองรับ

| งาน | ระดับของรายการ | ฟิลด์ที่ให้คะแนน Y1 |
|---|---|---|
| T1 | รายกิจกรรม + สรุปรายเอกสาร | งบจัดสรร · เบิกจ่าย · ร้อยละ · ผู้เข้าร่วม · ความครบถ้วน (+ 2 ยอดรวม) |
| T3 | รายกิจกรรม + สรุปรายเอกสาร | หน่วยงาน · งบจัดสรร · เบิกจ่าย (+ จำนวนกิจกรรม · ยอดรวม · ร้อยละรายหน่วยงาน) |
| T4 | รายเอกสาร | จำนวนกิจกรรม · จำนวนแล้วเสร็จ · งบรวม · เบิกจ่ายรวม · **ยอดคงเหลือ Q4** |
| T5 | ราย (กิจกรรม × กลุ่มเป้าหมาย) | ชื่อกลุ่มเป้าหมาย (+ จำนวนรวมรายเอกสาร) |
| T6 | รายกิจกรรม | ผู้เข้าร่วม · ร้อยละ · ควรตรวจสอบเพิ่มเติม |
| T7 | ราย claim + สรุปรายเอกสาร | ข้อความ claim · แถวอ้างอิง · ยอดเบิกจ่ายรวม · ข้อสังเกตความสอดคล้อง |

**สองรูปร่างที่ต้องเขียนโค้ดเป็นพิเศษ**

- **T5 ขยายแถว** — จำนวนรายการที่ถูกต้องไม่เท่ากับจำนวนแถวในอินพุต ต้องจับคู่ด้วย (รหัสกิจกรรม + ชื่อกลุ่มเป้าหมาย) ไม่ใช่ลำดับ
- **T7 รายการอิสระ** — จำนวน claim ไม่คงที่ ต้องแมปกับ `findings_allowlist` แทนการจับคู่หนึ่งต่อหนึ่ง
